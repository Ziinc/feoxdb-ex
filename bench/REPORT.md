# Benchmark report (PRD milestone 7)

**This is a preliminary, single-container smoke-scale run, not the PRD
section 9.6 dedicated-hardware benchmark.** It exists to prove the
harness (`bench/run.exs`) produces sane numbers, and to give a rough
sense of where `feoxdb_ex` sits relative to CubDB, Cachex, `:dets`,
`:mnesia`, and raw `:ets`. It is not a substitute for running the
harness on real, controlled hardware before publishing performance
claims.

> **Earlier versions of this report were wrong.** The harness picked
> each random key with `Enum.random/1` on a 20,000-element list, which
> costs ~80μs per call, so every read and mixed-workload number was
> about 80μs regardless of the store and the differences between stores
> were noise. Mnesia's data directory was also never applied, and stores
> were left open across scenarios. All of this is fixed (see
> `bench/README.md`), and every number below comes from the fixed
> harness. Don't compare them with earlier revisions of this file.

## How the run is set up

- Each system is opened, preloaded, measured, and closed on its own, so
  no other store's background work runs during its measurement.
- Every measured call asserts its result, and every preloaded key is
  read back before measurement, so failed operations can't be counted as
  fast successes.
- Random keys come from indexing a tuple, which costs well under a
  microsecond for every system alike.
- Durability settings differ between the disk-backed systems and are
  stated, not equalised:
  - CubDB: `auto_compact: false, auto_file_sync: true`, so it fsyncs
    every write.
  - `feox_persistent`: buffered writes persisted by background writer
    threads; no per-write sync.
  - `:dets`: `type: :set`, buffered writes; no per-write sync.
  - `:mnesia`: `disc_copies` table driven through the `dirty_*` API, the
    cheapest and least safe API Mnesia offers. The whole table lives in
    RAM, and writes go to a log dumped in the background.
- Every disk-backed store's `flush/1` runs once after preload, outside
  the measured window. No measured workload pays the cost of making
  writes durable.
- Same generated keys/values fed to every system.
- Benchee's warmup phase serves as the "discard first run" rule.

## Results

Full console + HTML output is regenerated by rerunning `bench/run.exs`
(`bench/output/`, gitignored). The tables below show medians; averages
and 99th percentiles are in the raw output further down.

Under `parallel: 4`, Benchee runs four processes that each call the
store in a loop, and reports the latency each process saw. Those
columns show latency under contention, not combined throughput.

Each workload is split into memory-backed systems (`:ets`, feox_memory,
cachex — no durability) and disk-backed systems (feox_persistent,
`:dets`, `:mnesia` with `disc_copies`, CubDB), since comparing across
that line is comparing different guarantees, not just different
implementations.

### Random read (workload 2)

**Memory-backed**

| System | parallel: 1 (median) | parallel: 4 (median) |
|---|---|---|
| `:ets` (control) | 0.59 μs | 0.55 μs |
| cachex | 0.86 μs | 0.92 μs |
| feox_memory | 4.46 μs | 19.6 μs |

**Disk-backed**

| System | parallel: 1 (median) | parallel: 4 (median) |
|---|---|---|
| mnesia | 0.56 μs | 1.01 μs |
| feox_persistent | 4.59 μs | 20.4 μs |
| dets | 7.54 μs | 59.8 μs |
| cubdb | 92.4 μs | 268.4 μs |

`feoxdb_ex` reads cost about 4.5μs at `parallel: 1`, roughly 8× an
`:ets` lookup, and get about 4× slower again at `parallel: 4`, while
`:ets`, Cachex, and Mnesia barely change. Memory and persistent modes
read at the same speed, because persistent mode serves reads from
memory too. Mnesia's dirty reads are a direct ETS lookup on its RAM
copy, which is why it matches `:ets`. `feoxdb_ex` is still well ahead
of `:dets` and CubDB, which read from the file.

The likely cause of the gap and the poor scaling: every `get`,
`insert`, and `delete` NIF runs on a dirty I/O scheduler
(`native/feoxdb_nif/src/store.rs`), so each call moves the calling
process to a dirty scheduler and back, and concurrent callers contend
for those schedulers. This hasn't been verified by profiling yet.

| System | parallel: 1 (median) | parallel: 4 (median) |

| `:ets` (control) | 1.11 μs | 2.12 μs |
| cachex | 1.58 μs | 2.43 μs |
| feox_memory | 3.95 μs | 27.5 μs |

**Disk-backed**

| System | parallel: 1 (median) | parallel: 4 (median) |
|---|---|---|
| dets | 1.37 μs | 7.46 μs |
| mnesia | 2.73 μs | 8.08 μs |
| feox_persistent | 6.59 μs | 24.6 μs |
| cubdb | 188.1 μs | 723.8 μs |

The medians hide large tails for the stores that buffer writes. `:dets`
has the fastest median but averages 33μs at `parallel: 1` and has a
5.8ms 99th percentile at `parallel: 4`. `feox_persistent`'s 99th
percentile is 429μs at `parallel: 1` and 1.1ms at `parallel: 4` (see
the backpressure finding below). CubDB is the only store syncing every
write, which accounts for some of its cost even on tmpfs.

This workload inserts a new key on every iteration, so each table grows
while it's measured, and faster systems end up with bigger tables.

## An observed finding: persistent-mode write buffer backpressure

This run printed 251,341 `feox: write entry for a N byte key has been
retried 8 times` warnings on stderr from the `feoxdb` crate. Every one
was for a 13–15-byte key, which only the write-only (`write:<n>`) and
delete (`delete:<n>`) scenarios generate; preloaded keys are at most 9
bytes, so preload, reads, and the mixed workload never triggered it.
The warning is FeOxDB's own write-buffer logging that it's retrying a
buffered write, not a crash. Every insert and delete still returned
`:ok`, which the harness now asserts.

This explains `feox_persistent`'s long write tail: under sustained,
uninterrupted write pressure, the background writer workers (PRD section
6, "100ms or 16MB per shard" flush window) fall behind and the write
path backs up. A production workload that sustains a similar write rate
against persistent-mode `feoxdb_ex` should expect the same behaviour,
and since this run used tmpfs, a real disk will likely make it worse.

Mnesia showed the same kind of pressure: 3,044 `Mnesia is overloaded:
{:dump_log, :write_threshold}` warnings, from its transaction log
filling faster than it could be dumped.

These findings should be validated against the PRD's own Section 9.5
scheduler-health methodology (not yet implemented — see
`bench/README.md`) before being treated as conclusive.

Benchee's memory and reduction counts are in the full run output but

## Caveats / what this run does not establish

- Single container, not the PRD's two dedicated hosts (`x86_64` +
  Apple Silicon).
- All disk-backed data files were on tmpfs (`/dev/shm`). A real disk
  (with or without `io_uring`) will behave differently, likely worse for
  every disk-backed store, and will make CubDB's per-write fsync much
  more expensive than it is here.
- No measured workload includes the cost of making writes durable, and
  no read touches the disk for `feox_persistent` or Mnesia, which keep
  everything in memory. There's no restart-and-read or recovery-time
  benchmark.
- `:mnesia` is exercised only via `dirty_read`/`dirty_write`/
  `dirty_delete` with a single `disc_copies` replica — not a
  transactional or multi-node comparison, which would show materially
  different (worse) numbers.
- No disabled CPU frequency scaling, unverified `io_uring` availability.
- One run per configuration, with no repeats or confidence intervals.
- Only 4 of the PRD's 8 workloads are implemented (see
  `bench/README.md`).
- Only one value size (64 bytes, the largest size the BEAM stores as a
  heap binary rather than a reference-counted one) was run; the PRD
  also wants 1KB and 64KB.
- No scheduler-health run (PRD section 9.5) is implemented yet.

Re-run `bench/run.exs` with a larger `BENCH_DATASET_SIZE`, the full
`BENCH_CONCURRENCY` list, and each of the three value sizes on
appropriate hardware before treating any of these numbers as
publishable.
